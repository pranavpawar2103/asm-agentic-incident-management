Agentic RAG Architecture

Executive Summary

This document outlines the architecture for an automated IT Ticket Resolution Agent. The system utilizes a Multi-Source Retrieval-Augmented Generation (RAG) framework combined with a ReAct (Reasoning + Acting) agentic workflow.

It synthesizes official ground-truth documentation with historical real-world workarounds to provide highly accurate, step-by-step ticket resolutions.

Phase 1: Data Ingestion & Context

The system relies on two distinct data sources, requiring different processing pipelines before indexing.

Contextual Retrieval

Standard chunking destroys document context. Before embedding, a lightweight LLM reads the entire page and generates a global summary prepended to every chunk.

Structural Chunking

Pages are split by structural headers (H1, H2, H3) rather than arbitrary character limits to keep complete thoughts intact.

Metadata Injection & Authority

Page breadcrumbs, author, and tags are attached. Marked as Primary Authority.

Entity Extraction

Tickets are strictly parsed into predefined fields: Issue Description, Error Logs, and Final Resolution. Arbitrary chunking is disabled.

Filtering & Authority

Only "Closed/Resolved" tickets are ingested to ensure accuracy. Marked as Secondary Authority.

Dual-Indexing Strategy

Every document passes through a dual-indexing pipeline to support hybrid search mechanisms.

Dense Representation
Text embedded into vectors to capture semantic, conceptual meaning.
Sparse Representation
Tokenized into sparse matrices (BM25) to guarantee exact-match lookups.

Phase 2: Query Transformation

Users typically write tickets describing symptoms, while documentation contains solutions. The orchestrator translates raw tickets into optimized search parameters.

Multi-Query Breakdown

The raw ticket is passed to an LLM which decomposes it into 3 to 5 highly targeted search queries (e.g., separating the specific error code from the overarching system failure). These run in parallel to ensure robust coverage.

HyDE Generation

Hypothetical Document Embeddings. The LLM writes a "fake resolution note" for the user's issue. The retrieval engine searches using this hypothetical answer—drastically improving semantic match rates.

Phase 3: Retrieval Pipeline

The pipeline executes a sophisticated three-stage search to retrieve the most accurate chunks.

Metadata rules are applied to restrict searches (e.g., limiting the search to the specific application's Confluence space based on the ticket's tags). This acts as a hard boundary to reduce noise.
Semantic (Vector) and Exact-Keyword (BM25) searches are executed simultaneously across both data sources (Confluence and Historical Tickets).
RRF mathematically combines the distinct scoring mechanisms of Vector and BM25 searches based on their rank order, ensuring documents that perform well in both searches rise to the top.
The top 20 fused documents are passed through a neural Cross-Encoder along with the original query. The Cross-Encoder calculates exact contextual relevance and truncates the list, passing only the absolute top 3-5 chunks to the final Agent.

Phase 4: ReAct Orchestrator

The system uses a ReAct (Reasoning + Acting) pattern, granting the LLM autonomy to investigate rather than simply dumping documents into a prompt.

Strict Conflict Resolution Rules

R1

The Official Standard

Confluence is the official standard. If Confluence provides a solution, it must be the primary recommendation.

R2

Conflict Handling

If Confluence and a Ticket conflict, explicitly state the discrepancy, recommend the Confluence solution as standard, but provide the Ticket as an alternative workaround.

R3

Missing Documentation

If Confluence lacks the answer, provide the Historical Ticket's resolution, explicitly citing it as a "past engineering workaround" along with the specific Ticket ID.

Phase 5: Final Output Generation

The agent produces a structured, user-facing response containing:

  • Root Cause Analysis: A brief explanation based on logs mapped to the retrieved context.
  • Resolution Steps: Clear, step-by-step actionable instructions.
  • References: Direct links to the Confluence SOPs and Historical Ticket IDs utilized.
