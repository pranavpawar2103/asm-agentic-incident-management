A4 · Closure Quality

Are the close notes worth reading?

rulesAIa personresult
Closure Qualityscores the notes, never blocks
New
A ticket is resolved or closed

One that went through our pipeline. History can be scored too, behind a switch.

1
Quick checks (rules)

Empty. Too short (provisional: under 40 characters). Only filler like "done", "fixed", "working now". Copy of the description. A test ticket is skipped, not scored. Rules can stop a note, never pass one.

One AI question, on the masked note

Report three things, each with an exact quote: what caused it, what was done, how it was checked. Level 0 none, 1 vague, 2 specific. A level without a real quote drops to 0. The AI never says pass or fail.

2
The code adds it up

Score out of 6. Provisional pass: steps at least 1 and total at least 4. Thresholds live in a file.

3
Low score: 1 to 3 short questions

"What caused it?" A better draft is built only from what is already on the ticket. Gaps stay as "[engineer to add: cause]". Nothing is guessed.

Engineer accepts, edits or rejects

Version 1 nudges only. Blocking the close is the client's choice, behind a setting that is off.

Score, what is missing, final notes

Notes that pass go on to Knowledge Builder. Nothing is written back to ServiceNow or JIRA yet.

New files

  • data/registry/closure_rules.yaml: filler words, minimum length, pass rule
  • A closure_score prompt in prompts.yaml
  • backend/app/agents/closure_quality/: config, rules, model check (same layout as Data Quality and Triage)
  • services/closure/ (a package, per review feedback), endpoints under /closure, tests
  • evaluation/closure_report.py and closure_cases.xlsx

Endpoints

  • POST /closure/run and /closure/tickets/{id}/check
  • GET /closure/queue: notes that need work, lowest score first
  • POST /closure/tickets/{id}/review: accept, edit (with the new notes), reject
  • GET /closure/report: how often engineers change the notes or the score

A limit to know

Our data has no ServiceNow work notes, only the resolution notes and the replies. So drafts can only reorganise what is there; the real fix is to ask the engineer.

A5 · Knowledge Builder

Turn good fixes into knowledge

Knowledge Builderdrafts, never publishes
New
Close notes passed, or the nightly run
1
Save the case so Resolution can find it

Masked: symptom, cause, steps, check, app, matched article, score. The cause and steps come from the Closure Quality answer, so no extra AI call.

2
Is there already an article? (rules)

First: the note cites a KB id that exists (33 of 34 do). Then: error codes and job names against each article's symptoms. Then: keyword overlap within the same app.

Not clear? One AI question

"Which of these articles (id, title, symptoms) describes this case, or none?" with a quote. The code checks that the id exists.

No article? Draft one

In the KB format: symptoms, root cause, resolution steps, escalation. From the masked case only. Unknown parts stay "[expert to add]".

3
Checks on the draft (code)

All four parts present. Every error code, ID and command appears in the source notes. No personal data in the text. Source tickets cited. A draft that fails is rejected, not shown.

4
Seen 3 times in 30 days?

Same app and issue: suggest a problem record with the linked tickets. Uses the same grouping as storms, over closed tickets.

An expert approves, edits or rejects

Approving gives the next id (for example KB-PAY-006) and exports the article as markdown.

Coverage that grows, per app

Articles, closed tickets matched, open gaps, drafts waiting.

New tables

  • resolved_cases: the masked case. The thing Resolution reads
  • kb_drafts: status draft, approved, rejected; the source tickets; the reviewer
  • problem_candidates: app, issue, linked tickets, status open, accepted or dismissed
  • A final_text column on the review table, so an engineer's edited notes are kept

Endpoints

  • POST /knowledge/run
  • GET /knowledge/coverage: per app, matched and unmatched
  • GET /knowledge/drafts, POST …/{id}/review, GET …/{id}/export (markdown)
  • GET /knowledge/problems, POST …/{id}/decision

Why "export", not "publish"

There is no Confluence here, and data/ is mounted read-only. So version 1 stores the draft and its status in the database and exports markdown to a separate folder. A Confluence call replaces the export later.

Risks

What could go wrong

Real notes are messier

Our test notes are written by us. Scores will look better than reality until the support lead labels real ones.

A draft that sounds right but is wrong

An expert must approve every draft. Code rejects any draft with a code, ID or command that is not in the source notes.

Names in notes

Masked on the way in and checked on the way out. A draft with any personal data is rejected.

Closed tickets are skipped today

Ingestion marks a ticket already closed on arrival as history and never processes it. We need a small change to pick up tickets resolved later, and a switch to score history.

Two readers of the KB

If Resolution and Knowledge Builder each parse the articles, they will drift. Decision 2 prevents it.

Reviewers are not verified

Reviewer names are typed in until there are logins, like the Triage review.
