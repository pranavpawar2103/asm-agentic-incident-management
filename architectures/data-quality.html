Plan · Data Quality agent · the first of three

Rules first. One call.
A person sends the email.

The agent decides whether an engineer can act on a ticket, names what is missing for that application, and produces the chasing email a person accepts, edits or rejects. The markdown source is docs/plan-data-quality.md.

code decides one model call a person decides

1 · The job

One ticket in seven cannot be worked. Someone chases it by hand.

Who, today, what hurts

The person on the AMS support rota opens every new ticket from ServiceNow, JIRA and the mailbox and decides whether it can be worked. In the sample, 15 of 100 cannot: "System not working. Please fix ASAP.", "cant login", a forwarded email with only a screenshot. The rota person reads it, guesses the application, writes a chasing email, and the ticket sits until the requester answers.

What the agent produces

One verdict per ticket: pass, needs_info, not_an_incident, service_request, or needs_review when the model is unavailable. A list of the specific items missing for that application with one plain question each. An assembled email a person accepts, edits or rejects and sends from their own mail client.

Never sendsNo email is sent and no ServiceNow or JIRA record is changed by the agent. It writes to this service's database only.
Never sees PIINothing on the client's PII class list reaches the model. It never sees the ticket number or the requester's name, and never writes the email.
Never holds a P1Urgent tickets get the same verdict and draft, and Triage selects them regardless of the data-quality outcome.
Never leaves CanadaModel endpoint in a Canadian region. Unverified for the model named below; only synthetic tickets until it is.
Assumptions, because the brief did not say
  • Trigger is ingestion: pending tickets whose latest run has no human decision or a changed input hash.
  • Per-app checklists are derived from the seven KB pages; the support lead corrects them.
  • The gate is the decision endpoint from the code review plus one HTMX page.
  • Volume unknown. The sample has 67 open tickets over 8 days, so 8 to 10 a day; 40 is the planning ceiling.
Measured before it was written

Candidate rules were run against all 100 tickets and the answer key.

  • Incomplete tickets caught by rules alone: 14 of 15, with zero false fails.
  • Good tickets cleared with no model call: 37 of 85.
  • Left for the model: 49. Every should-pass body is at least 63 characters; 14 of 15 should-fail are under 50 after signature stripping.

The taxonomy, fixed on day 1

The answer key's free text ("application, since when, how many users") is mapped to these 15 items so coverage is scored in code. The three borderline rows must not pass; needs_info or needs_review both count as caught.

Feedback loop

Every accept, edit or reject lands in agent_runs with its reason and the edited text. Weekly, a script pulls rejected and heavily edited runs into a review workbook for the support lead to label. Labelled rows join the holdout. Nothing is auto-promoted.

Code, call, or gate: each with its reason
  • prepare, rules, compose, record: code. Deterministic, auditable, run when AI is off.
  • assess: one structured model call. Needs language understanding of a 70-character email and app-specific questions.
  • gate: a person. Advisory only, by project rule. A status on the run row, not a framework interrupt.
  • Nothing in parallel. Nothing on its own clock; the two-day reminder is deferred.
On LangGraph

The original request asked for it, the design repo bans it, and the only thing it buys is resume on reply, which is v0.2. So v0.1 is run_ticket() calling five plain functions. When the reply path is built, the engineers evaluate LangGraph against "call the same function with the new text" and adopt it only if the resume semantics are worth a dependency and a second state store. The decision is dated in docs/adr/0001-orchestration.md and ARCHITECTURE.md is updated to match. The nodes do not change under either answer.

Why the protect stop exists

spaCy tags PayrollPro and OrderHub as organisations. Without the allow-list they would be hidden and the app guess would break. Without the keep-list, INV-2026-91226 looks like a phone number; the v0.1 regex ate it on five tickets. Protect runs before swap so the right things survive.

How we know it works

The redaction eval runs on all 100 tickets and on every change to recognisers, allow-list or threshold. It asserts no reporter, email or third-party name survives, every application name survives untouched, and every business identifier survives intact or as a typed token. Milestone 2, before any real ticket.

4 · Each step in detail

prepare and rules: what code decides, on what

Step 1prepare
codePresidio + spaCy NERapp guess
Redact with Presidio, in process

Presidio Analyzer with the spaCy large English model for PERSON and LOCATION, the built-in email and phone recognisers, and custom recognisers with context words for EMPLOYEE_ID and CUSTOMER_NAME. ORG is left out: spaCy tags PayrollPro and OrderHub as organisations and redacting them breaks the app guess. Every registry name and KB title is allow-listed. Nothing leaves the service, so residency is untouched.

Keep-list and reversible tokens

Order, invoice, SKU, PO, device and job identifiers are their own entity types with a higher score than the generic recognisers, so Presidio keeps them. Names and contacts are replaced ([REPORTER], [PERSON_n], [EMAIL], [PHONE], [SIGNATURE]). Employee IDs, customer names and locations become reversible tokens, [EMP_ID_1], [CUSTOMER_1], [LOCATION_1], with the mapping in redaction_tokens. Location is tokenised, not deleted, because it is a taxonomy item the model must see is present.

Threshold and model size

Presidio scores every finding; the threshold is chosen on the 100 tickets and re-checked on the first real batch. The phone recogniser uses the phonenumbers library with context, so INV-2026-91226 scores low instead of being swallowed as the v0.1 regex did on five tickets. The large model is used because the sample names are South Asian and the small models miss more of them; the transformer model is the fallback only if the eval demands it.

Application guess

From cmdb_ci or components when present, else the first keyword hit in data/registry/apps.yaml. Attachments by name only.

Redaction eval, milestone 2

On all 100 tickets, and on every change to recognisers, allow-list or threshold: no reporter name, email or third-party name from the workbook survives into the stored model input; every registry application name survives untouched; every INV-, ORD-, SKU-, PO-, device and employee identifier survives intact or as a typed token.

Six signals on every ticket first

body_length after signature stripping · app_found · identifier_found · attachment_only · summary_equals_body · mentions_previous_ticket. All six reach the model whichever rule fires.

Then the verdict, in order
  1. Test blocklist → not_an_incident. No email; flag for a person to close.
  2. Access or new-user request with nothing broken → service_request. No chase.
  3. body_length < 50 → needs_info. Every should-pass body is ≥ 63; 14 of 15 should-fail are under 50 after stripping. One is 49.
  4. body_length ≥ 60, app found, identifier found → pass. No model call.
  5. Otherwise uncertain → model call.

assess: the one model call

Step 3assess
one callstructured outputclaude-opus-5-5 · effort low
Inputs

Source, channel, application guess and whether it came from a system field, redacted summary (≤ 200 chars), redacted body (≤ 2,000 chars, truncated with a marker), attachment names, the six signals, the per-app checklist (≤ 300 tokens) or the generic one, the urgent flag. Not the ticket number. Not the name.

Output: verdict and one question per missing item
{ actionable: false, application: "PayrollPro" | null, not_an_incident: false, service_request: false, missing: [ { item: "symptom", why: "says 'check my salary' with nothing about what is wrong", question: "What looks wrong with your salary: the amount, a missing allowance, or something else?" }, { item: "period", why: "no pay period named", question: "Which pay period is affected, for example October 2026?" }, { item: "identifier", why: "no employee ID", question: "What is your employee ID, so we can look up the payslip?" } ], schema_version: 1 }

The model does not write the email. It does not see or produce the ticket number, the requester's name, or any address.

Validation, in code, after the schema check
  • actionable == false if and only if missing is non-empty or a flag is set; a flag implies missing is empty.
  • application in the registry or null; if the guess came from a system field, the model may fill a null, not overrule it.
  • 1 to 5 items, each in the taxonomy, unique.
  • Each question: ends with ?, ≤ 200 chars, no URL, no @, no digit run longer than 4, no redaction token, none of password, OTP, PIN, card number.
  • No question asks for an item the signals found present.

Status transitions

pass → dq_passed. Accepted or edited draft → needs_info. not_an_incident and service_request keep their names for a person to close or route. needs_review stays pending with the run visible on the page. Reject → the table above.

Idempotency

Unique on (ticket_id, agent, input_hash, prompt_version). Selection skips any ticket whose latest run has a human decision unless the input hash changed. A prompt bump never re-chases a requester; a reply always re-runs.

Hand-off to Triage

dq_verdict, missing[], application, urgent. Triage selects pipeline_status = dq_passed OR urgent = true: an urgent ticket that failed data quality is triaged and chased at the same time.

The agent needs a 300-token checklist per application, not search. The KB pages are read once offline to write the checklists. If a checklist grows past a few thousand tokens, that is the point to revisit.

Retention

Redacted input, model output, assembled email, edited_value (which may hold a first name) and the token map: 90 days, then deleted. Hash, verdict, decision, tokens and cost: kept. Raw ticket text lives in tickets.raw under its own retention.

Access

The service database and the review page are reachable by the rota team only. The answer key stays outside data/ so the pipeline can never read it.

6 · Guardrails

Advisory, redacted, switchable, audited, in region

PII

The class list comes from the client's privacy owner, not from this plan. Redaction is Presidio with spaCy NER, in process, logged per entity type, with an allow-list for application names and keep-list recognisers for business identifiers. The redaction eval runs in milestone 2 and on every change to recognisers, allow-list or threshold. Third-party names are covered by the NER pass from milestone 2.

Untrusted input

The ticket body is user-written and labelled as data. Schema-constrained output, no tools, the model never writes free text a person forwards, and the question validator rejects URLs, redaction tokens and credential words.

Advisory vs automated

Verdict and pipeline_status are internal state, written automatically. The email is advisory. Never automated: sending email, closing a ticket, routing a service request, any ServiceNow or JIRA write.

Kill switch

LLM_ENABLED (global, the design repo's one switch) and DQ_LLM_ENABLED (per agent), read from the environment or a settings row on every run, never cached at import. Off → assess skipped, verdict needs_review, the queue keeps moving.

Audit

One agent_runs row per run with everything under Stored. The proposed-versus-accepted gap, the metric the client asked for, is a query.

Residency and vendor

The first-party API cannot pin inference to Canada, so the route under the project rule is the vendor's Bedrock client in a Canadian region, if the model is served there. Refusal fallback on that platform is the SDK's client-side middleware. Verified by ______ on ______ before any real ticket.

7 · Operations

A CLI over 40 tickets a day. Boring on purpose.

Queue and idempotency

v0.1 is python -m app.agents.run data_quality, selecting as in record and processing in order. Idempotency is the unique key plus the selection rule. A scheduled background task is the v0.2 trigger; a queue table with SKIP LOCKED is the Postgres-day answer.

Model gateway

Vendor SDK, max_retries=2, timeout 60 s. Circuit breaker: five consecutive failures open it for the rest of the run and route to the fallback. The CLI exits per batch, so the breaker is per run; acceptable at this volume and written here so nobody expects more. Token usage read from every response.

Observability

Structured log per run: ticket id, request id, verdict, model, prompt version, latency, tokens, cost, skip reason, redaction counts. Dashboard, a SQL view: tickets per day, verdict mix, skip rate, accept / edit / reject with reasons, application accuracy on tickets with a system field, p95 latency, cost per day.

Versioning and runbook

Prompt hash is prompt_version; schema_version is in the output; template hash is template_version. Changing any creates new runs on undecided tickets only. Runbook headings: model down or breaker open · false-fail spike · redaction miss · re-run after a prompt change · rotating the key · turning the LLM off · clearing the 90-day data.

Human time replaced
